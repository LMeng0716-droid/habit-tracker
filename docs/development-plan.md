# 「每日进步」第一版开发计划

日期：2026-10-08。本文只规划未来开发，不执行应用初始化、依赖安装、运行或部署。功能口径以[产品需求](product-requirements.md)为准，来源与授权判断以[开源调研](open-source-research.md)为准。

## 1. 推荐方案及备选

**推荐：独立实现 React + TypeScript + Vite，原生CSS/CSS Modules，版本化JSON存储于localStorage。** 手机优先响应式布局；React内置状态/useReducer配合Context即可，首版不引入Zustand、后端和大图表库。React Router是否引入取决于是否要求详情独立URL；默认用轻量页面状态切换和明确返回动作，支持浏览器返回需纳入验收，不让返回直接丢未保存表单。

| 选择 | 理由 | 代价与适用边界 |
| --- | --- | --- |
| React + TypeScript | 指定参考项目均使用，可学习组件分工；类型帮助约束日期和存储格式 | TypeScript有学习成本，但比直接fork复杂成品可控 |
| Vite | 本地开发与静态构建简单，无服务器渲染需求 | 开发时重新核对稳定版本和Node最低要求，不直接复制调研项目旧版本 |
| CSS/CSS Modules | 一套样式规则，便于初学者定位问题 | 自己做好焦点、对比度和响应式；不同时引入MUI与Tailwind |
| localStorage | 文本型小数据、单写者、同步保存流程清晰 | 容量有限、阻塞主线程、可被清除；以50习惯/两年历史作为初始验证样本，无大附件；备份是P0 |
| Vitest + Testing Library | 日期/统计纯逻辑与交互测试 | 开发阶段安装，不在本次调研安装；浏览器验收另测真实存储 |

若必须支持大量记录、长日记、附件或异步事务，再迁移IndexedDB并采用小型封装，不能在localStorage里继续堆。若目标改为微信小程序需重新选工具链；若必须多端同步，先另做账户/服务端安全与冲突方案，不在首版偷偷追加。

Node选开发启动时仍受支持、且满足所选Vite版本的LTS，记录版本文件和锁文件；当前环境已有Node24/npm，不代表应用依赖已安装或构建已验证。React/TypeScript/Vite具体版本待开发任务锁定，未来使用npm ci复现。

## 2. 逻辑分层与数据契约（仅文字设计）

建议小型结构：pages放今天/详情/统计/设置，components放卡片/表单/月历/确认框，domain放日期和统计纯函数，storage放读取/写入/校验/迁移/导出。不要照搬DoHabit全部六层目录体系。

数据快照含schemaVersion、revision、habits、completionRecords。习惯含随机唯一id、名称、预设颜色、createdDate、createdAt、可选archivedDate；完成记录含habitId和本地date，以两者作为唯一键。归档当天已有记录的移除和归档标记必须同一次持久化提交，确认文案先说明影响。不存当前连续或完成率，让其由记录推导。

存储边界：启动时先验证再开放修改；损坏数据保留原文，进入恢复状态；每次修改先得到候选快照、校验并保存成功，再确认UI状态。捕获配额/权限异常；多窗口检查revision，发现外部写入使旧窗口只读并提示刷新。第一版不提供冲突自动合并，也不承诺极端同时写入的协作安全。

日期边界：本地年月日作为记录键，连续计算按日历前后一天，不以本地时间相减固定86400000毫秒替代日历运算；测试闰年和夏令时，防止换时区和DST破坏计算。统计函数接收“今天”参数，测试不依赖机器实际时间。旧记录不因跨时区改写。

备份边界：格式版本和文件大小先检查，合法性与引用检查后预览；支持整体替换，保存成功才展示完成；首次只支持v1，不预写空迁移逻辑冒充兼容。以后升级必须保留老版本备份和迁移测试。

## 3. 分阶段实施和完成标准

以下工作量为初学者单人投入的估算，不是承诺工期；包含学习、联调和返工。只有用户启动开发任务后执行。

| 阶段 | 预计投入 | 交付物 | 完成标准 |
| --- | --- | --- | --- |
| 0：确认边界与线框 | 0.5～1天 | 确认本地Web/每天一次；中文文案、页面线框、许可证策略 | 所有P0及日期/归档规则一致，不再包含云同步或复杂频率 |
| 1：工程和数据核心 | 1～2天 | 最小工程、日期/统计纯函数、数据结构、持久化与恢复状态 | 类型检查通过；跨周/月/年、今天未打卡规则、坏数据与保存失败测试通过 |
| 2：主要打卡流程 | 2～3天 | 今天页、创建/编辑、撤销、详情月历、归档/删除 | 完整主流程刷新后保留；未来/创建前禁用；手机和键盘可操作 |
| 3：统计与数据管理 | 1～2天 | 月度数值、JSON导出/替换导入、清空确认、归档历史 | 月有效天数准确；备份往返一致；无效导入不修改已有数据 |
| 4：发布前验收 | 1～2天 | 自动检查、浏览器验收记录、已知限制、使用说明 | 全部P0满足，build/type-check/test通过；审查后另行决定是否部署 |

总计约5.5～10个工作日；不含账户、推送、PWA、移动商店或云同步，也不在本次发布网站。

## 4. 测试矩阵

| 类别 | 必测场景 | 失败意味着什么 |
| --- | --- | --- |
| 日期 | 北京时间凌晨不落前一天；周日→周一；12月31日→1月1日；闰年2月29日；DST地区日历步进 | 主打卡数据或连续数不可信，阻止发布 |
| 连续 | 今天未完成但昨天完成；前天是最后记录；中间补记连接；撤销拆分；重复/乱序输入 | 当前/最长计算错误，阻止发布 |
| 月统计 | 月中创建；当前月截止今天；历史月完整；归档从当天排除；零分母 | 比率误导，阻止发布 |
| 持久化 | 新建/打卡/撤销刷新；配额错误；损坏JSON；未知schema；多标签变化提示 | 数据丢失或伪成功，阻止发布 |
| 备份 | 导出导入等价；超限文件；重复ID；不存在习惯引用；无效或未来日期；取消导入 | 现有数据可能被覆盖，阻止发布 |
| 交互 | 空状态；名称校验；确认删除/清空；归档当天记录处理；导入替换预览；未保存返回 | 操作不清晰或破坏数据，阻止发布 |
| 浏览器 | 手机Safari、Android Chrome、桌面Chrome/Firefox；360px；键盘和弹窗焦点 | 若兼容性未测试，明确未验证，不能写“所有设备支持” |

发布前最少一条真实浏览器端到端流程覆盖“创建→打卡→刷新→补记→撤销→导出→清空→导入”。可以先人工验收并记录浏览器/版本，后续再引入Playwright；不以零测试或lint通过替代功能验证。

## 5. 依赖与代码复用策略

第一版独立实现，不拷贝未授权项目代码或DoHabit/Loop/Habitica受copyleft约束的应用代码。以后如确实选择fork，应先确定项目整体许可证、源码提供渠道和素材授权，再调整计划。图标尽量使用文本/简单原创符号；需要图标库时核实许可并保留通知，不复制上游Logo、插画或截图作为应用资产。

依赖只加解决明确问题的包；锁文件入库，node_modules/dist不入库。代码开发时添加.gitignore与CI并验证npm ci、类型检查、测试、build；本次不生成这些工程文件。无需Docker、数据库、Redis、服务器或第三方API密钥。

## 6. 风险和后续决策

- 本地数据可被清除：首版说明和备份恢复都必须完成；IndexedDB也不能替代备份。
- 产品规则膨胀：如要每周频率或暂停，需要重新定义统计分母和连续，不先加菜单选项。
- 浏览器同时操作：第一版单写者、冲突提示；需要实时同步时另立项目。
- 缺少真实运行证据：本次所有上游运行体验均未验证；后续工程选型不能把README承诺当通过测试。
- 授权不明：上游缺LICENSE或素材单独限制时不复制；本项目许可证应在发布代码前决定。

本轮交付只含三份文档和审查用PR。开发、依赖安装、部署和PR合并均留待后续明确任务。
