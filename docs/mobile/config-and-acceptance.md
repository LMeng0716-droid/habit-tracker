# 公开配置安全与真实 Supabase 验收（2026-10-17）

## 配置与构建

当前只允许两个 `VITE_*` 变量：

- `VITE_SUPABASE_URL`：真实项目的 HTTPS 根地址。支持 Supabase 标准域名和有效自定义域名；禁止账号/密码、路径、查询参数、fragment、非标准端口、IP、保留示例域名和占位符。
- `VITE_SUPABASE_PUBLISHABLE_KEY`：项目的公开 `sb_publishable_...` key。拒绝 secret key、service_role、旧式 anon JWT、占位符及错误格式。

不要发送、提交或配置服务端密钥。本应用不需要数据库密码。JWT和刷新令牌也不能写入仓库、截图或验收报告。

本地复制`.env.example`到`.env.local`后填写独立测试项目的两项公开配置。**示例文件本身故意不能通过校验**。项目不读取或迁移旧打卡localStorage；Auth会话仍由SDK正常持久化。

`npm run check:config`读取生产模式环境，采用Vite的dotenv/进程变量优先级。`npm run build`先校验，再执行类型检查及Vite构建。直接执行`vite build`也由配置hook校验实际mode，不能绕过。生产模式缺少任一变量即非零退出；危险或错误配置在开发服务器中也停止，避免被注入浏览器。仅缺失配置的开发模式允许显示可操作的配置提示。

所有诊断只输出固定消息/变量名，不输出值。额外`VITE_*`一律拒绝，防止Vite自动公开无关变量；以后需要新增公开配置时须先修改allowlist并审核。未带VITE前缀的服务端环境变量不会因此公开。

校验只验证格式和泄密风险，**不验证远程项目存在、key是否属于该项目或数据库/API可用**。不要把CI合成值替换进生产设置。合成值只用于本地与PR构建，无真实项目授权；浏览器请求被测试拦截。

## GitHub Actions / Pages

发布时应在仓库 Settings → Secrets and variables → Actions → Variables，设置上述两项**仓库级公开变量**。仅在github-pages environment下设置变量，不保证build job可以读取，因为该environment目前属于deploy job。

Pages工作流在构建前单独运行校验，并且build自身再次校验。只给校验/构建步骤传入公开变量，不注入npm ci和测试步骤。失败后不上传artifact，也不进入依赖build的deploy job。未设置变量时必须失败，不发布配置提示页。

base仍为`/habit-tracker/`，认证跳转为页面origin加该base。部署仍只允许main；手机分支push只执行检查。本轮未修改main、触发部署、配置真实仓库变量或调用Supabase。

**注意：main上的旧工作流尚未包含本分支修复；未来合并将触发正式Pages发布，必须先另行批准。** 当前工作不会自动让新功能出现在正式网站。

## 真实测试环境准备

1. 使用habit-tracker-test，不使用生产项目。数据库结构本轮不变，不重跑迁移。按既有只读检查确认两表、五个RPC、RLS/FORCE RLS、权限及Data API的habit_mobile schema暴露。
2. 将测试项目URL和publishable key仅填入本地`.env.local`，运行`npm run check:config`及`npm run dev`。控制台认证回调加入实际本地地址，例如`http://localhost:5173/habit-tracker/`；保留正式地址，不必把Site URL改成另一个正式项目。邮件redirectTo由当前前端地址生成。
3. 真机使用可访问的测试预览地址。若从手机访问电脑，需使用实际局域网地址并允许对应测试回调；若要托管预览，需另行授权发布到测试入口。本轮不创建远程预览。正式旧页面没有新回调UI，不能拿返回旧页面的结果作为新版验收。
4. 开启Email注册和验证，确认邮件发送/SMTP及测试邮箱可收到。准备A、B两个不同邮箱。记录测试日期、浏览器和匿名化账号标识，不记录密码/key/JWT。

## 验收顺序与预期

### 注册、邮箱验证、登录和退出

1. 在新版测试入口注册A。预期提示查收验证邮件，未验证时不能读取业务数据（以项目验证策略为准）。
2. 打开邮件验证链接，确认返回同一新版入口而非正式旧页面。允许自动建立会话或手动登录；核对账号邮箱正确，首次显示空习惯列表。
3. 退出，页面立即清除习惯；错误密码登录显示错误，不出现旧数据；正确密码可重新登录。
4. “忘记密码”发送重置邮件，打开后应显示“设置新密码”，更新后测试旧密码失败、新密码成功。过期/重复使用链接应失败，不能误显示修改成功。

### 云端保存、刷新与恢复

1. A创建习惯，编辑名称/颜色，打卡、取消、再打卡。每次成功应显示已保存；刷新后状态一致。使用测试项目控制台只读查询确认两表实际记录，不以浏览器页面为唯一证据。
2. 检查历史日历、连续天数、完成率；新习惯创建前和未来日期不能打卡。历史补打需等有效日期积累后验收，不靠改生产日期或伪造创建日期。
3. 归档后当天及此前记录仍存在，历史只读。
4. 清除该网站浏览器数据，重新登录A，应恢复相同习惯和历史。换另一台手机登录A，刷新后应恢复同样数据，无需导入JSON或旧localStorage。
5. 断网保存显示失败且保留输入，不宣称成功。联网先刷新核对，再重试；重复打卡不产生两条记录。

### 用户隔离与真实JWT

1. B注册、验证、登录，只能读取B的数据。A/B可使用相同习惯ID测试，记录仍相互独立。
2. 用B自己的JWT在本地API工具调用A独有ID的edit_habit、archive_habit、set_checkin，均应失败；read_snapshot和直接表查询均不得返回A的数据或冲突详情。
3. B直接伪造user_id插入、修改owner/创建日期、修改已归档记录、写未来打卡均应被权限/RLS/trigger拒绝。
4. 无JWT、过期JWT及伪造签名JWT请求应失败。仅用publishable key不能获得A/B业务数据。不要使用SQL Editor管理员身份模拟上述请求。
5. A退出再登录B，不应显示A的数据，包含迟到的旧请求响应。

### 手机与发布门槛

在真实iPhone Safari验证键盘、触控、底部安全区域、月份选择器、邮件打开方式及清除数据后恢复；本地Chromium触控模拟不等于真机验收。全部通过后记录成功/失败项，再单独审核正式配置与部署，禁止先合并再补验证。
